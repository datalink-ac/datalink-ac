# datalink as context — 把数据放进链接里

> 这是一个理念的第一次正式表述。datalink.ac 已经上线，规范草案已经写好第一版。
> 这个 issue 是它的出处，也是讨论的地方。

## 一句话

**把数据放进链接里（data in the link）。**

不是数据的截图，不是仪表盘的入口——是数据本身，在 URL 里。
人打开链接看到图，agent 取到链接拿到数，操作的是同一串字符。

## 两种读法

**datalink as context** — 链接本身就是上下文，不是指向上下文的指针。
拿到链接的一方不需要「抓取 → 截图 → 转述」这一轮往返；它拿到的就是可以被直接推理的东西。

**datalink as agent context** — 对 agent 来说，链接就是接口。
它读链接、写链接、在链接上做计算。人和 agent 因此有了共同的界面：
一种双方早就知道怎么复制、修改和转发的格式。

## 三个主张

### 01 — 别再给模型喂截图

喂给模型最贵的东西是一张图。图表是「为眼睛做的表的有损压缩」，
图上没画的东西就没了，而模型被要求把它还原出来——靠 OCR，靠估算。

一张 705×500 的图作为图片大约 470 个视觉 token；装着同样数字的链接大约 20 个——数字就在链接里。
更贵的是准确性：图片没法告诉你单位、样本量、这个值是均值还是最大值。

数据链接同时给出渲染和数据。人和 agent 读的是同一串东西，中间没有翻译步骤，
所以翻译的时候什么也没丢。

### 02 — URL 就是 API

每一条数据链接都是从参数到「真相的一张图」的纯函数：
没有会话、没有登录、没有仪表盘、没有刷新按钮。

这带来三件白拿的东西：**缓存**（URL 就是键）、**版本化**（`v=1` 让输出不再变，
贴进 release note 的链接永远正确）、**可 diff**（两条链接差一个参数，就是一个可以被 review 的改动）。

人改链接是为了看，agent 改链接是为了算。谁都不需要学对方的软件——
因为共同的界面就是一条 URL。

### 03 — 图只是一种渲染，链接才是通用形态

「数据住在 URL 里」跟饼图毫无关系。同一套扁平参数已经能描述结构图、表格、日历、幻灯片。
换的是渲染器，不变的是链接。

## 第一个场景：GitHub

数据链接最先证明自己的地方，不是仪表盘，是那些**文字本来就在、图片本来就不在**的地方：

- **release note** — 「新增 2400 行，主要是 TypeScript」这句话本来就是一张表。
  做成链接，它同时是一张图，而且依然可 grep、可 diff。
- **issue** — 用三段话解释一个功能比一张图老得快；
  因为是链接，下一个人可以直接挪一个框，而不是开口要求重画。
- **pull request** — reviewer 真正会要的那张图（这次改了什么、动了哪些文件）。
  作为链接它是**可以审的**：在 PR 里改一个参数，图跟着变。截图没法被审。

理由很简单：那里的一切本来都是文本——一个 diff、一条评论、一份 release note。
数据链接不用任何人改习惯就能落进去。而且读 issue 的 bot 拿到的是数字，不是数字的照片。


## 还没解决的

规范里留着的开放问题，都值得在这里吵：

1. **规格要不要单独版本化？** 钉住渲染器还不够，语法也得钉住。
2. **规格要不要签名？** 怎么让 agent 分得出一张真图和一张伪造图？
3. **URL 装不下的数据怎么办？** 以及，把数据存到服务器上的隐私代价是什么？
4. **要不要有公开的渲染器注册表？** 让「数据链接」成为标准而不是约定。
5. **一条链接要不要按 `Accept` 协商输出？** 浏览器给 SVG，agent 给 JSON，而不是另开一条路径。
6. **怎么表达不确定性？** 估算出来的图和事实的图不是一回事，规格应该能说出自己是哪一种。

还有一条更硬的：**隐私**。数据链接天生公开——谁拿到字符串谁就拿到数据。
这条线划在哪里，是规范里还没写完的一节，也是博客里《URL 会暴露什么》那篇在想的。
