问题

图不是数据。

那张图

它显示，不保存

一张图能让你看出一百个数字的形状，但它没法把那一百个数字交给你。

那个模型

它读的是像素

拿到图片，模型靠「看」把数值还原出来。它很擅长这个——但它终究是在读，而且它分不清哪些是读出来的、哪些是补上去的。

那份产物

没有东西可核对

稿子发出去了，写它的上下文没有。下一个人来读——一个人、一个 agent、或者一年后的你——手里只有那张图，没有数据可以对照。

想法

把数据放进链接里——哪怕背后的服务挂了，这条链接说的还是它说的。

链接 数据就在里面

分享出去，对方拿到的是准确的 context，不是一张截图——他可以改，可以加评论，再分享。数字跟着链接走：放进 README、放进博文，哪怕背后的服务挂了，这条链接的内容仍然知道。stateless：不用账号，不依赖云端，不用一直跑着什么。

图 一眼就够

读者看到的：形状、趋势、占比，一眼就够，不用点开任何东西。视觉语言每次都一样，读者的注意力花在数据表达的意图上，而不是样式上。

数字 精确、可引用，不用「看」

agent 读到的：地址里那些数字本身。它不用从像素里重建数值，不用四舍五入，不花一个视觉 token。它引用那个数字，也可以拿它做计算。

两个读者

一条链接，两个读者，同一份数字。

人 · 看到图

  • 一图胜千言。 形状、趋势、占比——文字要写一段话才说得出的，图一眼就说完。
  • 易于分享、修改、扩展。 贴进 README、博文、issue，对方拿到的不是一张截图：是一份准确的 context——他能改、能加标注，再合作。
  • 后面是一个 app。 打开 explore，改一个参数，图立刻就变；想换成别的画法，也在里面换。

agent · 拿到数据

  • 精确。 数字本身——不四舍五入，不 OCR，不从像素上估。
  • 无幻觉。 它读数据，不编数字。
  • 省钱。 链接约 25 个 token，同一张图写成 SVG 约 1,100 个。取一次，上下文窗口不占。

存储与记忆

不再需要图片存储，也不需要保持一致性。数据链接是一行文字：数字一改，图跟着变—— 仓库里不再堆着一张张「改了也不知道改了哪儿」的图，同一份数据的每个副本也就都跟得上。

聊天记录里的一张图是条死路：背后的数字没了，后来的人只能从像素上把它重建回来。 链接把数字留住——而且参数本身就说明了当时在量什么、怎么量的。 所以一份报告不只是给人看的，它也是能被 agent 再次拿去用的记忆，而不是只能被相信。

读者拿到什么

一份看起来做完了的报告

图都出自同一个渲染器，每次都长一个样——不是 agent 当天随手拼出来的样子。

背后留下什么

还装着数据的链接

每张图都是一条链接，数字在里面。一路上什么也没被压平。

往后意味着什么

能被重新读回来的记忆

半年之后，有记忆的 agent 读那条链接，能读出当时的意图和数字，而不只是它们的照片。

两个场景

两种不用再付的成本。

场景一

你的 README 里有数据

今天。 数字变了，图就得重渲染、重上传、再当二进制提交一次。仓库在胖，而 diff 只说「图片变了」，不说变了什么。

用数据链接。 agent 改链接里的一个数字，提交。diff 里就是那个数字，图跟着变；一年后提交历史还说得清你当时的意思。

场景二

同一份文档要出好几种语言

今天。 六种语言，六张图文件，六次渲染，六次提交——而数据每改一次，就要做六遍。

用数据链接。 语言只是一个参数。六张图，六条 URL，每条一行文字——由同一个 agent 从同一份来源生成。

还可以是什么

不只是图表。

每个标签页都是一条链接。datalink.ac/draw 和 x-cmd.com/draw 是同一个服务，区别只在地址。点任何一张图，都能在 explorer 里打开，手动改。

它最合适的地方，是 GitHub。
